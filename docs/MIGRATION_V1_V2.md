## 1. Parité des moteurs (preuves)

### 1.1 SKU — identique à 100 %
- Règle V1 : `legacy-v1/server.js` `generateSKU` (l. 80-89), format `[MODEL][YY][S]-[MAT][OPT]-[COLOR]`.
- Règle V2 : `api/src/services/sku.ts` `assembleSku` — même format, mêmes défauts.
- **Test sur données réelles** : les **285 variantes** de `legacy-v1/data/products_db.json` passées dans
  `assembleSku` redonnent **exactement** le SKU stocké par la V1. `285/285, 0 écart`.

### 1.2 ID référentiel — règles V1 portées
- Règles V1 : `legacy-v1/public/app.js` (l. 1757-1872) — `configPrefixMap`, `skuCategoriesConfig`,
  `autoGeneratedCategories`.
- Portage V2 : `api/src/services/sku.ts` `generateRefId(category, name, existing)` réplique fidèlement :
  - **models** → `AA###` (préfixe fixe, pad 3) ;
  - **colors** → `###` (pad 3, ignore les codes ≥ 900 ; 999 = Noir réservé) ;
  - **globalMaterials** → `CU###` / `CE###` (CE si « exceptionnel/exotique ») ;
  - **options/sizes** → `##` ; **optionTypes** → `###` ;
  - **years** → 2 derniers chiffres ; **seasons** → `H`/`E` ;
  - **materials, skinTypes, linings, materialDetails, suppliers, jewelry, origins, hsCodes, ateliers**
    → `PREFIX-###` (MAT-, TDP-, DOU-, DMA-, FOU-, BIZ-, PAY-, CHS-, ATE-).
- Branché sur **Admin → Référentiel → « Générer »** (le libellé alimente les règles années/saisons/CU-CE).
- **Tests** : 7 cas dans `api/src/services/sku.test.ts` (total 19/19 verts).

> Conséquence : la V2 est un **sur-ensemble** du moteur V1 (mêmes ID + incréments séquentiels que la V1
> n'avait jamais terminés, ex. la couleur qui saute le 999).

## 2. Audit d'architecture V1 (pourquoi elle ne peut pas être un socle « solide » en l'état)

| Dimension | V1 (`legacy-v1/`) | V2 |
|---|---|---|
| Langage | JS monolithe — `server.js` **1 395 l.** + `public/app.js` **2 817 l.** | TypeScript modulaire (back + front) |
| Persistance | **Fichiers JSON** (`products_db.json`, users JSON) via `fs.writeFileSync` + Mongo partiel | **PostgreSQL + Prisma** (transactions) |
| Durabilité | **Éphémère** sur Render (FS non persistant) → risque de perte/corruption | Base gérée, migrations versionnées |
| Auth | **Aucune** : mots de passe en clair dans le JSON (`"admin"`, `"1234"`), pas de JWT/bcrypt | bcrypt + JWT + autorisation par route/rôle |
| Écritures | Non atomiques (réécriture de fichier complet) → corruption concurrente | Transactions Prisma |
| Maintenance | Patch par remplacement de chaînes (86 hotfix historiques) | Modules typés + tests + revue par diff |
| Shopify | API figée `2024-01`, REST | GraphQL + pagination cursor, service de sync |

**Conclusion** : faire de la V1 un socle solide impose d'abord une **Phase 0** (auth serveur + migration
Postgres + dé-monolithisation). Or c'est précisément le cœur déjà livré en V2. Bâtir les nouvelles
features sur la V1 sans cette Phase 0 reviendrait à **réintroduire les risques 🔴** listés dans `CLAUDE.md`.

## 4. Options de convergence

### Option A — **Converger sur la V2** (recommandée)
1. ✅ Parité moteurs prouvée (SKU + ID) — **fait**.
2. Migration de données V1 → Postgres (catalogue, matières, clients déjà sur Shopify).
3. Run parallèle : V1 = prod / V2 = pré-prod jusqu'à parité fonctionnelle ressentie par l'équipe.
4. Bascule unique + retrait V1. → **une seule session = celle-ci**.
- **Coût** : faible/moyen (le gros est fait). **Risque** : faible. **Perte** : nulle.

### Option B — Converger sur la V1
1. Phase 0 obligatoire : réécrire auth + persistance Postgres + casser le monolithe (= refaire la V2).
2. Re-porter PLM, POS vignettes, médias/commentaires/workflow, OPS dans une base JS.
- **Coût** : élevé. **Risque** : élevé (régressions sur l'outil qui vend aujourd'hui). **Perte** :
  on jette le travail V2 déjà solide. Contredit la charte `CLAUDE.md`.
